# SDD Output Directory Configuration

All SDD artifacts generated by the agent MUST be written to a structured output directory **within the current workspace**. Never write artifacts to locations outside the workspace root, and never write inside the plugin's own directory.

## Output Structure

```
<workspace-root>/
└── output/
    └── {project-name}/
        ├── feature_spec.md          <- Step 1
        ├── requirements.md          <- Step 2
        ├── svs.md                   <- Step 2
        ├── stories.md               <- Step 2
        ├── plan.md                  <- Step 3
        ├── initiative_confluence.md <- Step 4
        └── jira/                    <- Step 4
            └── backlog.yaml
```

## Rules

1. **Workspace-relative output.** The `output/` directory lives at the **current workspace root** (the folder opened in Cursor). All artifacts go under `output/{project-name}/`. Never write to the plugin's install directory.

2. **Project name derivation.** Use the feature or initiative name as the project folder, converted to `kebab-case`. Examples:
   - "Saved Views for Reports" -> `output/saved-views-for-reports/`
   - "Per-Tenant Data Residency" -> `output/per-tenant-data-residency/`

3. **Step sub-folders (optional).** For large initiatives with multiple phases, use step sub-folders:
   ```
   output/{project-name}/
   ├── feature_spec.md
   ├── requirements.md
   ├── phase1-platform-readiness/
   │   ├── svs.md
   │   └── stories.md
   ├── phase2-migration/
   │   ├── svs.md
   │   └── stories.md
   ├── plan.md
   └── initiative_confluence.md
   ```
   Use step sub-folders when the initiative has explicitly defined phases. For single-phase features, keep everything flat.

4. **Never write outside the workspace.** If the workspace contains multiple repos (multi-root), write to the `output/` folder under the **first workspace root**. Never write to a sibling repo's directory.

5. **Announce the output path.** When creating the first file for a project, tell the user:
   > "Writing artifacts to `output/{project-name}/`. All subsequent step outputs will go to this directory."

6. **Existing output.** If `output/{project-name}/` already has files from a previous run, do NOT overwrite without asking. Inform the user and ask whether to overwrite or create a versioned directory (e.g. `output/{project-name}-v2/`).

7. **Gitignore suggestion.** If the user does not want SDD artifacts committed, suggest adding `output/` to `.gitignore`. Otherwise, commit them so the spec history is versioned alongside code.

## User Override

If the user specifies a custom output path (e.g. "write to `specs/my-feature/`"), honor that path instead. The custom path still must be within the workspace root.
